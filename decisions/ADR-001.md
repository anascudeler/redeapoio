# ADR-001 — Escolha da stack de backend

## Status

Accepted

## Contexto

O projeto precisa de um backend simples de manter, com tipagem forte (o produto lida com dados
sensíveis — senhas, localização, alertas de emergência), fácil de evoluir incrementalmente por
fases, e com um ORM que reduza risco de erro em relacionamentos (a entidade `SupportRelationship`
tem duas referências para `User`, o que exige modelagem cuidadosa).

## Decisão

Backend construído com Node.js + Express + TypeScript, acesso a dados via Prisma ORM, banco MySQL,
autenticação via JWT.

## Motivo

- Express: framework maduro, simples, sem opinião excessiva sobre estrutura — adequado a um MVP que
  não deve ganhar complexidade arquitetural desnecessária.
- TypeScript: reduz erros em contratos entre camadas (Controller → Service → Prisma), importante
  dado que o domínio tem relações não triviais.
- Prisma: gera tipos a partir do schema, lida bem com relações duplas (como as duas FKs de
  `SupportRelationship` para `User`), e faz migrations de forma controlada.
- MySQL: banco relacional, adequado ao domínio (entidades com relacionamentos claros, sem
  necessidade de schema flexível).
- JWT: permite autenticação stateless, simples de validar em cada request via middleware, sem
  necessidade de sessão em banco no MVP.

## Consequências

- Toda query de banco passa por Prisma — não se escreve SQL cru nem se acessa o banco diretamente
  nos controllers.
- Mudança de banco (ex.: para Postgres) é possível no futuro trocando o `provider` do datasource,
  mas não é uma necessidade atual e não deve ser antecipada.
- A modelagem de `SupportRelationship` com `requesterId`/`supporterId` precisa de nomes de relação
  explícitos no Prisma para evitar ambiguidade entre as duas FKs para `User`.
